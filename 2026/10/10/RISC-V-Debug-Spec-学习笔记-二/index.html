调试通路

  • DTM（Debug Transport Module）：JTAG TAP 这一级，负责把 JTAG 移位转成对 DM 的 DMI 读/写。
  • DMI：DTM 与 DM 之间的简单串行总线（地址 7 位 + 数据 32 位 + op 读/写）。
  • DM（Debug Module）：实现调试状态机、寄存器和对 hart/总线的控制。

关键寄存器

DTM 寄存器

  • dtmcs 0x10:
    • version [3:0]：DTM 规范版本。通常为 1 (v0.11) 或 2 (v0.13)。OpenOCD 通过此位判断使用哪种调试协议。
    • abits [9:4]：DMI 地址位宽。决定了 DMI 地址寄存器的实际有效位数（通常为 7）。OpenOCD 据此计算 DMI 事务的地址掩码。
    • dmistat [11:10]：DMI 操作状态。是OP的拷贝。
      • 00：上一次 DMI 操作成功。
      • 10：上一次 DMI 操作失败（通常是时序违例或 DM 未响应）。
      • 11：DMI 总线忙。
    • idle [14:12]：建议的 DMI 空闲周期数。当 JTAG 时钟频率远高于 DM 内部时钟时，OpenOCD 会读取此值并在 DMI 事务间插入额外的 idle 周期以匹配时序。
    • dmireset [16]：DMI 软复位。写 1 可复位 DMI 状态机，清除 dmistat 错误。OpenOCD 在初始化或检测到 dmistat 错误时会自动写入此位。
    • dtmhardreset [17]：DTM 硬复位。写 1 会将整个 Debug 模块复位到初始状态。通常由 OpenOCD 在连接建立初期使用。
    • errinfo [20:18]：错误信息。当 dmistat 为失败（10）时，此字段提供失败原因（如地址无效、超时等）。
  • dmi 0x11:
    • address [abits+33:34]：DM 的MMIO寄存器地址。
    • data [33:2]：32位的数据。
    • op [1:0]：
      • 上位机写 dmi:
        • 0：忽略dmi的 data 和 address.
        • 1：read from address.
        • 2：write data to address.
      • 上位机读 dmi:
        • 0: success
        • 2: fail
        • 3: busy

DM 寄存器

  • dmcontrol 0x10:
    • haltreq : 请求 halt core
    • resumereq : 请求 resume core
    • hartreset : 请求 reset core
    • {hartselhi,hartsello} : 20位 core id
    • dmactive : 激活 DM 模块/DM 模块处于激活状态
    • 其他
  • dmstatus 0x11:
    • hart的状态由此寄存器表示。
  • abstractcs 0x16:
    • busy [12]: 抽象命令执行状态。
    • progbufsize [28:24]: 硬件实现的 buff 个数，0-16
    • datacount [3:0]: 硬件实现的data寄存器个数,0-12, 64位架构至少 2个
  • command 0x17:
    • 抽象命令

建立调试链接并探索设备特性

1. remote_bitbang

  • handle_target_init_command / riscv_init_target: OpenOCD 开始初始化目标架构（RISC-V），分配内部数据结构并注册回调。
  • remote_bitbang_init: 初始化 remote_bitbang 适配器驱动，并通过 TCP 连接到本地端口 9824（通常对应 Spike 或 QEMU 模拟器的 JTAG 端口）。
  • adapter_init: 提示该虚拟适配器不支持动态配置时钟频率（JTAG TCK 速度）。

这部分是为了建立TCP连接。

2. JTAG 链路扫描与 TAP 发现

  • jtag_add_reset: 释放 SRST（系统复位）和 TRST（测试复位）信号线，准备进行 JTAG 通信。
  • jtag_init_inner / jtag_examine_chain: 初始化 JTAG 链路，执行 DR 扫描以拦截 IDCODE 或 BYPASS 指令，从而发现链路上的 TAP（Test Access Port）控制器。
  • jtag_examine_chain_display: 成功发现 TAP，读取到 IDCODE 为 0xdeadbeef。解析出制造商为 0x777 (Fabric of Truth Inc)，这是 Spike 模拟器默认的虚拟 ID。
  • jtag_validate_ircapture: 验证 IR（指令寄存器）捕获, IDCODE地址为0x01.

这部分是与 DTM 建立连接。

3. DAP初始化

3.1 调试接口初始化（L103-107）

  • dap init: 初始化 Debug Access Port (DAP)。虽然这是 ARM 架构的术语，但 OpenOCD 的 RISC-V 调试后端复用了部分 DAP 框架以统一调试接口。
  • target_examine_one: 开始对目标核心进行深度探测（Examination），这是识别芯片特性（如寄存器数量、触发器、XLEN 等）的前置步骤。

3.2 DTM探测（L108-116）

OpenOCD 首先通过 JTAG 读取 DTMCS (Debug Transport Module Control and Status) 寄存器，以确定调试传输层的规格。

  • DTMCS: 0x0 -> 0x71: 写入 0，读回 0x71。
  • version=1_0: 0x71 的高位指示 DTM 版本为 1.0（对应 RISC-V Debug Spec v0.13 或 v1.0）。这决定了 OpenOCD 后续使用 riscv013 后端驱动。
  • abits=7: 地址位宽 (Address bits) 为 7 位。这意味着 DMI (Debug Module Interface) 的地址空间有 $2^7$ 个寄存器（地址范围 0x00 - 0x7F）。

必须获取 abits 后，DTM 模块 才能正常组织 DMI 事务，以便访问 DM 模块。

3.3 DM探测（L117-122）

OpenOCD 开始探测核心的 Debug Module (DM)。

  • Allocating new DM: 为当前核心分配 DM 数据结构。
  • read: dmcontrol=1 {dmactive=active}:
    • 读取地址 0x10 的 dmcontrol 寄存器。
    • 读回值为 1，解析出 dmactive=active。
    • 含义：Debug Module 当前已经处于激活状态（Spike 模拟器通常默认激活，或保留了之前的状态）。

4. DM 复位

DM 的复位在 Spec 上有描述：只操作dmcontrol.dmactive： write 0 -> read 0 -> write 1 -> read 1.

5. core 数量探测

core 的数量在 Spec 上提供了探测方法。向 20 位的 {hartselhi，hartsello} 写入最大值（每个bit为1），读回的值为 HARTSELLEN, 这表示hartsel的有效值范围。其次对每个 core 进行确认，dmactive=active 表示 core 存在。

6. 探索 抽象命令/progbuff

  • hartinfo 寄存器地址为0x12, dataaddr=0x380, datasize=2, dataaccess=1, nscratch=1. 也就是说使用memory来访问data寄存器，2个32位 memory 空间来表示 data0/data1 寄存器。memory 地址位 0x380. 使用程序缓冲 progbuff load/store 时，0x380/0x384就表示data0/data1.
  • sbcs 返回0值，表示不使用系统总线。
  • abstractcs 解析后，datacount=2, progbufsize=2. 表示 data0/data1 被实现了。progbuf 只有2个32位 SRAM 空间。这和 hartinfo 匹配。

7. core 架构探索

  • line 214-225, 确认XLEN值。通过 riscv013_execute_abstract_command 抽象命令, 按照 regno=0x1008（x8），aarsize=64bit 方式访问，查看抽象命令，发现执行成功。说明XLEN=64是可以正常执行的。
  • line 227-251, 通过XLEN只读取misa，并再次确认 XLEN 的值（misa包含了该值）。
  • line 252-342, 读取 vlenb, 确认VLEN。先通过mstatus.vs打开对向量寄存器的访问，然后读取vlenb寄存器。VLEN = vlenb * 8 = 128
  • line 343-412, 探测AIA扩展。1. 通过抽象命令读取mtopi, cmderr=3(exception); 2. 降级使用 progbuf 执行指令来代替。2.1 先保存fp（s0/x8）, 然后执行 progbuf 中的程序 0xfb002473;0x00100073 ，解码为csrrs s0, 0xfb0, x0; ebreak. 执行3次，cmderr=3, 都失败了。

至此，target create riscv.core riscv -chain-position riscv.cpu 创建完成。

多 core 控制

在设置resumereq之前，先设置了 hawindowsel = 0, hawindow = 0xf, 地址分别是 0x14, 0x15. 分组为：hartid=0~32, mask=0xf, 也就是hartid=0-3. 选择这几个同时控制，可能是smp开启的原因。
