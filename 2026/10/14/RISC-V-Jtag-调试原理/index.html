IR/DR 链

什么是 IR/DR 链

openocd 如何利用 IR/DR 链

openocd 建立连接配置如何。

newtap是建立一个测试访问接口，每个 DTM 有一个唯一的 expected-id，这是硬件绑定的值。 irlen 表示 ir 链指令宽度（即IR寄存器地址宽度）。JTAG 规范要求，指令宽度4~8位，riscv 采用5位。这里建了4个 core 目标，组合成 smp.

默认情况下 openocd 链接后会不断 poll harts 状态，不能手动扫描 ir/dr 链，即手动执行 irscan/drscan. 需要先用poll off停止 poll.
irscan 命令就是让jtag的状态机走一遍 ir 链，将指令（instruction）写入 ir 寄存器，即更新指令。这里 0x1 在 riscv 架构下是 IDCODE 指令，实际上就是 IDCODE 指令地址。
drscan 命令就是让jtag的状态机走一遍 dr 链，写入/读出指令对应的数据。上述命令表示读出 IDCODE.

irscan/drscan 是所有上层命令的基础。所有上层的命令，如 reg/mdw 等最后都会拆解成多个irscan/drscan来一起完成对应的功能。

IR 指令

下面的寄存器是 RISCV DTM 的部分寄存器。

Address Name Description Spec. Section
0x01 idcode To identify a specific silicon version Section 6.1.3
0x10 DTM Control and Status (dtmcs) For Debugging Section 6.1.4
0x11 Debug Module Interface Access ( dmi) For Debugging Section 6.1.5
0x1f bypass JTAG requires this encoding Section 6.1.6

从 JTAG 规范的角度，所谓 IR 指令实际上就是这些寄存器的地址值。比如 IDCODE 指令，指令编码为 0x1, 即地址值。DMI 指令，编码为 0x11. 当需要切换指令时，需要走一遍 IR 链。

DR 链扫描

当设置了 IR 指令后，需要通过 DR 链来完成指令背后的数据访问。就如上面的 IDCODE 指令。通常，IDCODE/DTMCS 指令只在最初建立连接时使用。而调试时走 DMI 指令，所以 IR 链在调试时基本上不会。

在jtag连接目标设备后，通常hart处于halted状态。openocd 会不断poll hart的状态，如下。

line 2750/2751 进行了2次 DR 链扫描。line 2752 解析的结果是，读 dmstatus 寄存器。读 dmstatus 行为本身是读 DM 模块的寄存器，DM 是一个独立的系统，地址空间与hart是分离的。一次 dmstatus 状态读取行为，被2次 dmi 事务完成。第一次，请求 dmstatus 读取，第二次，空操作，目的是读出返回的 dmstatus 值。所以进行了2次 DR 链扫描。

DMI 事务解析

下面是 DM 模块的部分寄存器，它们管理所有DM调试行为。

0x04 Abstract Data 0 (data0) Section 3.14.14
…
0x0f Abstract Data 11 (data11)
0x10 Debug Module Control (dmcontrol) Section 3.14.2
0x11 Debug Module Status (dmstatus) Section 3.14.1
0x12 Hart Info (hartinfo) Section 3.14.3
0x14 Hart Array Window Select (hawindowsel) Section 3.14.4
0x15 Hart Array Window (hawindow) Section 3.14.5
0x16 Abstract Control and Status (abstractcs) Section 3.14.6
0x17 Abstract Command (command) Section 3.14.7

0x27 Program Buffer 7 (progbuf7)

41b r 00000000 @11 -> + 00000000 @00; 0i : <位数>b <操作码> <输出数据> @<输出地址> -> <响应标志> <输入数据> @<输入地址>; <IDLE TCK 数>i

  • 41b：本次扫描的位宽为 41 位。这正是 RISC-V DMI 的标准长度：操作码 2 位 + 数据 32 位 + 地址 7 位 = 41 位。
  • r / -：DMI 操作码。r 表示 Read（读请求），- 表示 No-op（空操作，用于取回上一次请求的响应）。
  • 00000000：32 位数据字段。
  • @11 / @00：7 位地址字段，十六进制。@11 即地址 0x11，对应 dmstatus 寄存器；@00 即地址 0x00。
  • -> +：-> 分隔输出与输入；+ 表示本次扫描的响应有效（即输入数据来自 DMI 的响应）。
  • ; 0i：本次COMMAND执行后，在IDLE状态插入0个TCK，即在IDLE状态停留TCK数。

读 dmstatus 的 DMI 事务是通过配置 dmi(0x11) 寄存器完成的（DMI 指令），address = 0x11, data = 0, op = 1(read)，DR 链扫描同时，TDO 输出上一次 DMI 事务的响应值。返回 dmstatus 值时，再次发起了 DR 链扫描，address = data = 0, op = 0(忽略data/address), 同时 TDO 输出真正的返回值，data = 0x00430382, address = 0x11, op = 0(success，由“+”得到)。

实际上，一次高级指令的完成，还伴随其他操作，比如 resume 操作会执行了指令 fence.i; fence rw,rw，然后才写 dmcontrol.resumereq = 1. 而 fence.i; fence rw,rw 是 progbuf 执行的，会涉及到抽象命令等，会进行多次 DR 扫描，而不单单只是 dmcontrol 相关的 DR 扫描。

访问 hart 资源

Spec 中描述了 riscv 的调试系统，该系统有2种访问 hart 内部资源（GPRs, CSR, memory)的方式，一种是抽像命令，另一种是SBA总线方式（绕过hart）。因为调试系统（DTM+DMI+DM）是一个独立于 hart 的系统，DM模块的寄存器可以通过JTAG命令直接访问，但是 hart 中的资源需要间接访问：抽象命令或SBA总线访问。

SBA 总线访问

SBA 总线访问比较简单，DM 模块有 sbaddress0~3, sbdata0~3 寄存器，只要将目标内存地址和数据按规范的流程更新到这些寄存器即可。

抽象命令

抽象命令是调试模块的基础功能。包括3种抽象命令类型:access register, quick access, access memory. 以下是读misa（0x301）寄存器的过程。

  • line 230， riscv013_execute_abstract_command 执行了虚拟命令，这个命令是 access register=0x320301 {regno=0x301 write=arg0 transfer=enabled postexec=disabled aarpostincrement=disabled aarsize=64bit}。采用CSR访问类型，regno=0x301，这是 misa 的地址；write=arg0，表示从csr读数据到data0/data1；transfer=enabled，表示读的行为需要执行；postexec=disabled, 表示读CSR之后不需要执行程序缓冲区；aarpostincrement=disabled，表示读操作发生后地址不用自加（以便读取后续地址的数据）；aarsize=64bit, 表示数据是64位的。
  • line 232 41b w 00320301 @17 -> + 00000000 @00; 1i: 从这行信息上看，这里发生了一个 TCK 等待，然后再发起了检查busy读请求。这行信息表示，向 DM 模块的 command 寄存器（0x17）写数据 0x00320301, 同时上次的 DMI 事务的响应被 TDO 输出。这里进行了一次 DR 链扫描，可见，写 DM 模块寄存器只进行一次 DR 扫描。DM 模块在收到这个抽象命令后，对命令进行解析，然后根据 write,transfer等字段信息，开始从csr读取信息到arg0(data0/data1)。
  • line 234/235 41b r 00000000 @16 -> + 00320301 @17; 0i, 41b - 00000000 @00 -> + 02001002 @16; 0i: 这是在读取 DM 模块的 abstractcs 寄存器（0x16），这是在确认 busy 字段是否被置高，也就是抽象命令是否执行完了。这里进行了两次 DR 链扫描。
  • line 239/240 41b r 00000000 @16 -> + 00000000 @00; 0i,41b - 00000000 @00 -> + 02000002 @16; 0i: busy字段已经拉低，抽象命令执行完了。这里进行了两次 DR 链扫描。
  • line 244/245 41b r 00000000 @04 -> + 00000000 @00; 0i,41b r 00000000 @05 -> + 0034112d @04; 0i: 向 DM 模块的 data0/data1(0x4，0x5)寄存器读数据。因为抽象命令执行完成，data0/data1 已经被更新了。所以读 data0(0x4) 时，输出为 0x0034112d, 读 data1(0x5) 时，输出为 0x80000000. 所以就有了 misa = 0x800000000034112d.

程序缓冲区

这段日志是 progbuf 的执行过程。执行了指令 fence.i; fence rw,rw，整个过程进行了7次 DR 链扫描。

  • line 2550 41b w 0000100f @20 -> + 00000000 @00; 0i: 0x20 是 DM progbuf0 寄存器。指令为 fence.i.
  • line 2555 41b w 0330000f @21 -> + 00000000 @00; 0i: 0x21 是 DM progbuf1 寄存器。指令为 fence rw,rw.
  • line 2558/2560 41b w 00241000 @17 -> + 00000000 @00; 7i：写了抽象命令。regno=0x1000，指向的是 x0; transfer=disabled, 表示读写行为不执行。postexec=enabled, 表示在读写CSR之后需要执行程序缓冲区。此时，DM 模块解析命令并执行程序缓冲区(上述2条命令)。7i 表示 command 写完后需要在 IDLE 状态等待7个TCK，这主要是给时间给hart去执行代码，7个 TCK 之后，再查看了 busy状态。
  • line 2562/2563, 这是在确认程序缓冲区执行状态。

DMI命令

上述命令严格按照 Spec 给的流程进行测试。每次执行 dmi_read/dmi_write 指令都回触发 DR 链的扫描，最后回到 IDLE 状态。

emu 访问jtag接口

emu上访问jtag采用虚拟接口vjtag方式。实际上就是通过 monitor 向 JTAG port (TMS/TDI/TDO) 串行灌输信号。其本质还是通过 TMS 来推动 DUT 内部 IR/DR 链（状态机）的扫描。具体而言，monitor 上会开辟 sram 空间。tcl 命令会封装 irscan/drscan 接口，它们负责将 dmi 数据下载到 monitor 的 sram 上，monitor 会自动转换成 JTAG PORT 的串行信号（TMS/TDI/TDO）发到 DUT.
